Billing API:
Idempotency, CQRS and Streaming

Two legacy behaviours that look like bugs, and are really design problems.

Two design problems

A double-click double-bills

No duplicate protection anywhere: two clicks queue two runs.

A whole run in memory

Invoice endpoints load every invoice, for firms with 40,000 accounts.

The replacement: idempotent start-run, vertical slices, problem details, constant-memory listing and export.

Idempotency has to be enforced where the data is.

The client sends a key

Sketch · target design
POST /api/v1/billing/runs
Idempotency-Key: 3f2c9d1e-5b7a-4c1e-9a0d-8e6f2b1c4d77
Content-Type: application/json

{ "FirmId": 1, "PeriodEnd": "2026-09-30" }

One unique key per logical operation. The same key on every retry.

The server keeps a table of keys

Sketch · target design
CREATE TABLE dbo.IdempotencyKeys
(
    Scope        varchar(50)     NOT NULL,   -- e.g. 'StartBillingRun'
    [Key]        varchar(100)    NOT NULL,
    RequestHash  varbinary(32)   NOT NULL,
    RunId        int             NULL,       -- the stored result
    CreatedOn    datetime2       NOT NULL,
    CONSTRAINT PK_IdempotencyKeys PRIMARY KEY (Scope, [Key])
);

The primary key is scope plus key: the database guarantees a key is stored once.

Three outcomes

New key

Do the work. Store the key and the result.

Same key, same hash

Replay the stored result: same run ID, no second run.

Same key, different hash

A key reused for a different request: 422.

What exactly do you hash?

Not the raw bytes

Whitespace or property order differ; a byte hash calls identical requests different.

A canonical form

Firm ID, period end, run type: fixed order, fixed format. A retry from another client library still matches.

Lifetime and scope

  • Keep keys long enough for any realistic retry: a day interactive, longer for batch
  • Clean them up with a scheduled job
  • Scope the lookup by the caller's tenant, so a key only replays a result the same tenant created

One local transaction

Key without run: a retry returns a run that doesn't exist.

Run without key: a retry creates a second run.

The constraint closes it

COMMITfails: duplicate key (2627 / 2601)
catch → roll back → read A's result
Both callers get the same run ID. One run.
Sketch · target design
catch (DbUpdateException ex) when (ex.InnerException is SqlException { Number: 2627 or 2601 })

What the replay looks like

  • The same status code and body as the original
  • Optionally, a header saying the result was replayed
  • Enqueuing is quick, so blocking the loser is fine
  • Minutes-long operations: store the key as in-progress, return a conflict to a duplicate that arrives mid-flight

A natural key: necessary

The unmodified AngularJS app sends no idempotency header. Only a business rule can stop its double-click.

Sketch · target design
CREATE UNIQUE INDEX UX_BillingRunQueue_Firm_Period_Type ON dbo.BillingRunQueue (FirmId, PeriodEnd, RunType);

RunType is a new column: regular, rerun, shadow. A deliberate rerun is still possible.

…but not sufficient

Natural key

Business uniqueness: one regular run per firm, period end, run type.

Idempotency key

Retry safety: the same response, and "I'm retrying" vs "I really want another run".

You want both.

Two practical warnings

Existing duplicates

The index fails if production already has duplicate runs. Given FB-247, it probably does. Clean first, as its own reviewed step.

Filtered indexes

Inserts need the quoted identifier setting on; a procedure keeps the setting it was created with. Check how legacy procs were deployed.

Offset vs keyset paging

Offset (skip/take)

Skipped rows are still read: page 80 costs 80 pages of reads. Inserts between requests skip or repeat rows.

Keyset (cursor)

Rows after the last one you saw: an index seek every time, stable under inserts.

Rows after the last one you saw

Sketch · target design
var page = await db.Invoices
    .Where(i => i.RunId == runId && i.Id > cursor)
    .OrderBy(i => i.Id)
    .Take(pageSize)
    .Select(i => new InvoiceRow(i.Id, i.AccountId, i.Amount, i.Status))
    .ToListAsync(cancellationToken);
database/billing/001-schema.sql
CREATE NONCLUSTERED INDEX IX_Invoices_RunId ON dbo.Invoices (RunId);

A non-unique non-clustered index carries the clustered key (Id), so (RunId, Id) is seekable.

Cursor rules

  • An opaque next-page token (really the last ID, encoded)
  • Clients pass it back without interpreting it: the sort key can change later
  • The server caps page size, whatever the client asks
  • 50,000 rows on screen: keyset paging + virtual scrolling (lesson 22)

Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How do you make a POST idempotent?

Answer out loud.

Model answer
  • Client sends an idempotency key header
  • Server stores key, request hash and result in the side effect's transaction, with a unique constraint
  • Same key + body → replay; same key, different body → 422
  • Concurrent duplicates: the loser catches the duplicate-key error and returns the winner's result
  • Proven with concurrent requests against a real database
Question 2 of 5

Isn't a unique constraint on firm and period enough?

Answer out loud.

Model answer
  • It stops the double-click, and protects the AngularJS screen that sends no key
  • It can't give an API client a safe retry with the same response
  • It can't tell a retry from a deliberate rerun
  • Both: natural key (firm, period end, run type) + idempotency key
  • Clean existing duplicates before adding the index
Question 3 of 5

Offset or cursor paging?

Answer out loud.

Model answer
  • Cursor (keyset) for anything large or changing
  • Offset slows as the offset grows; skips or repeats rows when data changes
  • Keyset: rows after the last ID seen, an index seek, stable under inserts
  • Offset is fine for small, static lists
Question 4 of 5

How do you export 50,000 rows without loading them into memory?

Answer out loud.

Model answer
  • Project to a narrow row type; enumerate with AsAsyncEnumerable
  • Write each row to the response stream as it arrives, async throughout
  • Dispose the writer asynchronously; format with the invariant culture
  • Legacy built a whole DataSet, formatted by the downloader's browser culture
Question 5 of 5

Do you need MediatR for CQRS?

Answer out loud.

Model answer
  • No: CQRS is separating commands from queries
  • A handler interface, one handler per use case: about 50 lines
  • Minimal API endpoints inject handlers directly
  • MediatR went commercial in 2025; every dependency needs a licence review
