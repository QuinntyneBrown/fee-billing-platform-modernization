Login belongs to the legacy app

legacy/FeeBilling.Web/Web.config
<authentication mode="Forms">
  <forms loginUrl="~/Account/Login" name=".FEEBILLINGAUTH" timeout="120" slidingExpiration="true" />
</authentication>
  • Custom membership provider over the app's own user tables
  • The ticket is encrypted and signed with the machine key
  • Only ASP.NET on .NET Framework can read it

The machine key

legacy/FeeBilling.Web/Web.config
<!-- Shared across the web farm (and now also by the SystemWebAdapters remote-auth endpoint). -->
<machineKey validationKey="7E2B3F7A4C1D9E8F…"
            decryptionKey="A1B2C3D4E5F60718…"
            validation="HMACSHA256" decryption="AES" />

Every IIS node

Must share the key, or one node can't read another node's cookie. ClientX has its own key in Web.ClientX.config.

ASP.NET Core equivalent

A shared Data Protection key ring, handled just as deliberately.

The previous team's choice

Remote authentication

  • No change to the legacy login page
  • Works with Forms authentication exactly as it is today

A Forms ticket is a different format from what ASP.NET Core cookie authentication reads, so option two would mean changing how legacy issues its cookie first.

Legacy side: the remote-app server

legacy/FeeBilling.Web/Global.asax.cs · Application_Start
// Strangler-fig migration (2025): the ASP.NET Core services behind the YARP gateway call
// back into this app to resolve the Forms-auth user (remote authentication).
// Every request to Accounts.Api costs a round-trip to here.
SystemWebAdapterConfiguration.AddSystemWebAdapters(this)
    .AddProxySupport(options => options.UseForwardedHeaders = true)
    .AddRemoteAppServer(options => options.ApiKey = ConfigurationManager.AppSettings["RemoteAppApiKey"])
    .AddAuthenticationServer();

Web.config also registers SystemWebAdapterModule as an HTTP module, which is how the adapters see requests in IIS.

New side: the remote-app client

src/FeeBilling.Accounts.Api/Program.cs
// Login is still owned by the legacy app (Forms auth). Each request resolves the user by calling
// back into legacy (SystemWebAdapters remote authentication), so this API is down whenever legacy is.
builder.Services.AddSystemWebAdapters()
    .AddRemoteAppClient(options =>
    {
        options.RemoteAppUrl = new Uri(builder.Configuration["RemoteApp:Url"]
            ?? throw new InvalidOperationException("RemoteApp:Url is not configured."));
        options.ApiKey = builder.Configuration["RemoteApp:ApiKey"]
            ?? throw new InvalidOperationException("RemoteApp:ApiKey is not configured.");
    })
    .AddAuthenticationClient(true);

true makes remote authentication the default scheme for the whole app.

One request, two hops

The price

Every authenticated request to the new service costs one extra round trip to the old service.

That's what not changing the legacy login costs.

Caching the answer

Saves

Remember which user a cookie belongs to for a minute or two, and skip the call.

Costs

Logout or an account lockout isn't seen until the entry expires. Roles decide who can approve invoices.

Decide the window deliberately and write it down. Check what the adapters already do first.

Even the health endpoint fails

docs/handover.md
If IIS is down, Accounts.Api returns 500 on everything, including `/health`.
  • Likely cause: remote auth is the default scheme, and UseAuthentication runs for every request, anonymous or not
  • A health check that depends on another system is a bad health check
  • Liveness fails → the orchestrator restarts healthy pods in a loop

Remote session

  • Core app fetches session values from legacy at the start of a request, writes changes back at the end
  • AddSessionClient on the Core side, AddSessionServer on the Framework side
  • Every session key is registered with its type, so both sides serialize it the same way
  • Endpoints opt in; the session is locked for the whole request

Close the public path

Gateway catch-all

Forwards every path to IIS, including the remote-app endpoints the adapters add. Reachable from the internet unless blocked.

Internal address

RemoteApp:Url points straight at the legacy app, not at the gateway. Good. The public path still needs closing.

Make health independent

  • Pass false to AddAuthenticationClient: remote auth is no longer the default scheme
  • API endpoint groups require authorization with the remote scheme explicitly
  • Health and liveness stay anonymous and never call legacy
  • A timeout on the remote call, and an alert on its latency

Testing without legacy

tests/FeeBilling.Accounts.Api.Tests/Infrastructure/AccountsApiFixture.cs
builder.UseSetting("RemoteApp:Url", "http://legacy.invalid");
builder.UseSetting("RemoteApp:ApiKey", "not-used-in-tests");

builder.ConfigureTestServices(services =>
{
    // Replace SystemWebAdapters remote authentication (which calls the legacy app).
    services.AddAuthentication()
        .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>(TestAuthHandler.SchemeName, _ => { });
    services.PostConfigure<AuthenticationOptions>(options =>
    {
        options.DefaultScheme = TestAuthHandler.SchemeName;
        options.DefaultAuthenticateScheme = TestAuthHandler.SchemeName;
        options.DefaultChallengeScheme = TestAuthHandler.SchemeName;
    });
});

Why PostConfigure?

Configure

Callbacks run in registration order. The app already set its default scheme with AddAuthenticationClient(true), so a test's Configure can lose.

PostConfigure

Runs after every Configure callback, so the test scheme reliably wins.

The kind of detail that passes on one machine and fails on another.

What the green tests prove

Proven

The authorization rules, with a fake identity.

Not proven

The real handshake with legacy. Add an environment-level test on Windows, with the legacy app running.

A bridge, not a destination

Write the exit into an ADR with a trigger and a date, so the bridge doesn't quietly become permanent.

Interview drill

Four questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 4

How do old and new apps share a logged-in user during a migration?

Answer out loud.

Model answer
  • Remote authentication: the new app asks legacy on each request
  • Shared cookie: compatible middleware and a shared key ring
  • External identity provider with OpenID Connect first
  • FeeBilling: remote auth, because ASP.NET Core can't read a Forms ticket
  • Long-term target: OpenID Connect
Question 2 of 4

What are the trade-offs of remote authentication?

Answer out loud.

Model answer
  • Upside: zero change to the legacy login; works today
  • An extra round trip on every authenticated request
  • Legacy down means the new service is down, even /health
  • Legacy load grows as more traffic migrates
  • The endpoint and API key become security-sensitive
Question 3 of 4

How do you share session state between ASP.NET and ASP.NET Core?

Answer out loud.

Model answer
  • The adapters' remote session: fetch values from legacy, write them back
  • Every key registered with a serializer on both sides; locked per request
  • Slow, so first check whether session is needed at all
  • FeeBilling's legacy code doesn't use session: don't add it
Question 4 of 4

How do you test an ASP.NET Core service whose authentication depends on another app?

Answer out loud.

Model answer
  • Replace the scheme in WebApplicationFactory with a test handler (TestAuthHandler)
  • Include a test that an anonymous request gets a 401
  • Say explicitly: this doesn't test the integration
  • Cover the real handshake with an environment-level test, legacy running
