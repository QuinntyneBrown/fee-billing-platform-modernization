One idea to keep in mind

A shared library has two separate constraints

Language version

The C# the library is compiled with.

API surface

The APIs it is compiled against.

People mix these up. That difference is exactly what the interviewer is probing for.

How .NET is released

  • A new major version every November since .NET 5
  • Even numbers are LTS: three years of patches
  • Odd numbers are STS: extended to 24 months, per the training plan

All dates as of September 2026. Check Microsoft's support policy page before quoting them.

The dates that matter for FeeBilling

Windows components, on the Windows lifecycle

Not dying, but frozen. 4.8.1 is the last version.

Why .NET 10 and not .NET 8?

Start on .NET 8 today and you upgrade again within months, in the middle of the first migration.

Wasted effort, and wasted risk.

Already on .NET 8? Upgrade that first

.NET 8 → .NET 10

Mostly a target framework change and package bumps. Cheap.

.NET Framework → .NET 10

The real project.

  • A quick win that builds the upgrade pipeline everyone follows
  • Budget an LTS-to-LTS upgrade every two years: routine, not a project

## Decision

- New services target **.NET 8 (LTS)**.
- Shared libraries consumed by legacy target **`netstandard2.0`** until no .NET Framework project references them.

.NET 9's end date has moved since this was written, too.

The old decision stays as written: it records why .NET 8 was reasonable in March 2025.

.NET Standard is a contract, not a runtime

The contract

A versioned list of APIs that implementations promise to provide.

The implementations

.NET Framework, modern .NET, Mono, Xamarin

A netstandard2.0 library runs on any implementation that supports version 2.0 of the contract.

Why 2.0 specifically?

Version.NET FrameworkModern .NET
netstandard2.0Yes: the highest version Framework implementsYes
netstandard2.1Never implementedYes
netstandard2.2Won't exist: .NET Standard is frozen

New code targets net10.0. netstandard2.0 survives only as the bridge to .NET Framework.

A version detail worth knowing

.NET Framework 4.6.1 – 4.7.1

Claimed netstandard2.0 through shim assemblies. Binding-redirect pain.

.NET Framework 4.7.2+

Support is built in.

FeeBilling runs on 4.7.2: the right side of the line.

A bonus: netstandard2.0 is a guardrail

  • System.Web isn't part of netstandard2.0
  • So the shared library physically can't reach for HttpContext.Current, the way FeeBilling.Core does
  • Target it at net472 "because legacy needs it" and you lose that protection
  • Compatibility packages (like the one that brings ConfigurationManager to modern targets) quietly reopen the door
Language version vs API surface

Consumers of a library see compiled IL, not C# syntax.

The library's language version mostly doesn't matter to them. Its API surface does.

Not a contradiction

Compiler features

File-scoped namespaces, is not null: compile to ordinary IL. The C# 7.3 consumer never sees them.

The type's public shape

Must be something a C# 7.3 project can use. That's what the comment really means.

Nullable annotations don't protect legacy callers

  • The compiler emits attributes
  • A C# 7.3 consumer simply ignores them
  • Legacy code gets no warning for passing null

Different implementation, same API

Sketch · target design
public static void NotNull(object? value, string name)
{
#if NET
    ArgumentNullException.ThrowIfNull(value, name);
#else
    if (value is null) throw new ArgumentNullException(name);
#endif
}

The rule

  • Conditional compilation for implementation differences only
  • Public API identical across targets
  • Behaviour identical across targets

When do you drop netstandard2.0?

When the last net472 consumer is retired:

  • Retarget FeeBilling.Domain to net10.0
  • Delete the polyfills
  • Use modern APIs freely

Put it on the decommission checklist, so the transition tool doesn't become permanent.

Pin the SDK

{
  "sdk": {
    "version": "10.0.401",
    "rollForward": "latestFeature",

Traps

  • Trusting the ADR over the code, or the code over the ADR
  • Editing an accepted ADR's decision in place
  • Targeting the shared library at net472 "because legacy needs it"
  • Adding packages to Domain casually
  • Letting the two targets of a multi-targeted library diverge
  • Keeping netstandard2.0 forever
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

Why .NET 10 and not .NET 8?

Answer out loud.

Model answer
  • .NET 8 support ends November 10, 2026; .NET 10 is LTS until November 2028
  • Starting on .NET 8 means a second upgrade mid-migration
  • Move anything already on .NET 8 first: cheap, and it builds the upgrade pipeline
Question 2 of 5

How do legacy and new code share types during a migration?

Answer out loud.

Model answer
  • A shared library targeting netstandard2.0: Framework 4.7.2+ and .NET 10 both reference it
  • No System.Web, Entity Framework or logging, and netstandard2.0 helps enforce it
  • FeeBilling.Domain appears in both solutions
  • Retarget to net10.0 when the last Framework consumer is gone
Question 3 of 5

What's the difference between .NET Standard and .NET?

Answer out loud.

Model answer
  • .NET Standard: a versioned API contract
  • .NET Framework, modern .NET, Mono: implementations
  • Frozen at 2.1; Framework only implements 2.0
  • New code targets net10.0; netstandard2.0 is just the bridge
Question 4 of 5

Your shared library needs DateOnly, init setters or records. What now?

Answer out loud.

Model answer
  • DateOnly: use DateTime with a date-only convention, like BillingPeriod
  • Init setters and records: IsExternalInit polyfill, but not on types legacy constructs
  • Genuinely need newer APIs? Multi-target netstandard2.0 and net10.0
  • Identical public API and behaviour; differences behind conditional compilation
Question 5 of 5

What would you do in your first week about the target version?

Answer out loud.

Model answer
  • Check the code: every modern project targets net10.0, ADR-0002 still says .NET 8
  • Write a new ADR that supersedes it: .NET 10 for services, netstandard2.0 for shared libraries
  • Record the reason: .NET 8's end-of-support date
  • Confirm global.json pins the SDK locally and in CI
