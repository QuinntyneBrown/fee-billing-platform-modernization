Why not just fix the failing tests?

Making them pass proves nothing about Q3 2026 invoices.

Leave them alone. Build the harness that does prove something.

Characterization test

Describes what code actually does, not what someone thinks it should do.

  • Run the existing code on known inputs
  • Record the outputs
  • The recordings become the expected results

Michael Feathers, Working Effectively with Legacy Code

Failure is data

  • A calculation throws? Record the exception type, and keep going
  • An Outcome column: OK or the exception type name
  • "Legacy throws" becomes an expected result the new system must match, or consciously change

Compare as decimal, never as strings

Sketch · target design
decimal legacy = 5312.5m;    // double path, cast to decimal at the end
decimal modern = 5312.50m;   // decimal path, rounded to two places
legacy == modern;                          // true
legacy.ToString() == modern.ToString();    // false: "5312.5" vs "5312.50"

Write the file with a fixed two-decimal format, parse it back as decimal, compare numerically.

Explained isn't the same as fine

  • Each difference needs an entry in a known-differences allowlist
  • Linked to an ADR or a ticket
  • With the legacy policy: zero differences, full stop

Governance

Sketch · target design
# .github/CODEOWNERS
/golden/   @billing-leads
  • Golden files are committed; changing one is a reviewed act
  • The legacy runner runs on Windows, only when someone deliberately regenerates
  • Parity tests run on every pull request, in the Linux job

When the golden file changes

  1. Re-seed the database
  2. Regenerate on Windows, in a fresh process
  3. Review the diff line by line

New rows for a new scenario: expected

A change to an existing row: red flag. Legacy didn't change.

Traps

  • Refactoring legacy to make it testable first
  • Calling the fee calculator directly
  • Multithreading the runner
  • Letting the cache leak between runs
  • Current-culture golden files; comparing money as strings
  • Letting "legacy throws" crash the runner
  • Accepting golden-file changes in one big unexplained diff
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How do you know the new system is correct?

Answer out loud.

Model answer
  • Golden-master tests on the fee engine
  • Contract tests on the APIs
  • Shadow runs in production for a full billing cycle
  • Every difference fixed, or accepted with sign-off and a reason
Question 2 of 5

How do you test code that has no tests and can't be unit tested?

Answer out loud.

Model answer
  • Characterization tests
  • The narrowest seam that runs the code unchanged: FeeBilling's fake HttpContext
  • Known inputs in, recorded outputs become the expected results
  • No refactoring first: I'd be measuring my changes
Question 3 of 5

What's a golden master?

Answer out loud.

Model answer
  • Recorded, reviewed output of the current system for a fixed input set
  • Differences fail the build unless categorized and allowlisted with an ADR
  • Golden-file changes reviewed, e.g. through code owners
  • Inputs recorded too: no database in the modern test
Question 4 of 5

The new engine differs from legacy by one cent on seven accounts. What do you do?

Answer out loud.

Model answer
  • Categorize: one policy dimension back to legacy at a time
  • Legacy policy target is zero: fix the engine until it matches
  • Intended changes: allowlist, ADR, dollar impact per firm, sign-off
  • Ship separately, behind a flag
Question 5 of 5

Why not just fix the failing legacy tests?

Answer out loud.

Model answer
  • They assert 2016 data and need a database and an HttpContext
  • Some share a process-wide cache; some depend on today's date
  • Passing proves nothing about this quarter's invoices
  • Fixing them changes legacy before its behaviour is captured
