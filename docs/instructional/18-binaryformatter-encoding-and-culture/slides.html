Three silent breakers

BinaryFormatter

Remote code execution risk. Removed in .NET 9.

Encoding.Default

ANSI code page on Framework. UTF-8 on modern .NET.

Culture

Parsing follows the thread's current culture.

The payload names the types

Why it's dangerous

  • Attacker controls the bytes → chooses which types are created, in what state
  • Gadget chains: ordinary framework types whose constructors and callbacks combine to run code
  • Deserializing untrusted BinaryFormatter data = remote code execution
  • No configuration makes it safe on untrusted input

"But it's our own database."

Not a trust boundary. Anyone who can write to StagedBatches can run code in the ingestion process:

  • SQL injection somewhere else
  • A compromised account
  • A misconfigured tool

The timeline

.NET 5

Marked obsolete

Later releases

An error by default in more project types

.NET 9

Implementation removed. Always throws PlatformNotSupportedException

An unsupported compatibility package brings it back. Ban that too.

Coupled to a type name

The migration is about to change that assembly name and namespace.

Migrating: first, stop new writes

Stage the raw file, not your parse of it.

The CoreWCF host from lesson 17 writes the original bytes to Blob Storage. Nothing to deserialize.

Rows already staged · option 1

A one-time .NET Framework 4.7.2 tool

  • Framework can still run BinaryFormatter
  • Deserialize each row with a serialization binder that allows exactly two types: the list and Position
  • Reject everything else; re-serialize to JSON

Rows already staged · option 2

System.Formats.Nrbf (introduced with .NET 9)

  • NrbfDecoder reads the stream as a tree of class and array records with named fields
  • Never loads or instantiates the types they name: safe on .NET 10
  • Verify the record shapes against a real payload first

Either way: a format marker on each row, so old and new coexist during the switch.

Never use the default

Sketch · target design
Encoding.RegisterProvider(CodePagesEncodingProvider.Instance);   // once, at startup
var encoding = Encoding.GetEncoding(1252);                        // from the source's configuration
var text = encoding.GetString(content);
  • The code-page provider ships with modern .NET; .NET Standard needs System.Text.Encoding.CodePages
  • The encoding is part of the file format: configure it per custodian source

Culture-sensitive parsing and formatting can behave differently for each user.

NLS to ICU

.NET Framework on Windows

Culture data from the operating system: NLS

.NET 5+ (Windows too)

Culture data from ICU, and it varies by ICU version

On one .NET 10 machine: fr-CA groups with a non-breaking space; fr-FR with a narrow non-breaking space.

Containers: invariant globalization

Small images often run with no culture-specific data.

Depending on settings, creating fr-CA may even throw. Check your image.

The lesson

Culture data isn't a file format specification. The file format defines how numbers are written, not the server, and not the browser.

…but not perfect

ToUpper is culture-sensitive

Under tr-TR, lower-case i becomes İ, so nbin becomes NBİN. Use ToUpperInvariant.

Only three parts kept

NBIN_20260930_POS_FR.txt: the FR marker is silently dropped.

More silent breakers

  • FeeCalculator cache key uses ToShortDateString
  • CsvExporter formats values with the server's current culture
  • "C" under the invariant culture prints ¤, not $
  • JSON casing and serializer behaviour
  • EF Core: no lazy loading, different query translation
  • System.Drawing is Windows-only
  • Distributed transactions: Windows and an opt-in

Proving the fix

Culture theory

Run under en-CA, fr-CA and tr-TR. The parser gives the same answer in each.

Both seed files

Invariant and French files produce identical positions: 12 lines, including Côté, Jean at $609,471.47.

A symmetric fixture hides the bug

legacy/FeeBilling.Tests/Ingestion/CustodianFeedServiceTests.cs
private static byte[] File(params string[] lines)
{
    return Encoding.Default.GetBytes(Header + "\n" + string.Join("\n", lines));
}

The service decodes with Encoding.Default.GetString. Both ends change together on .NET Core, so the test can't see it.

Use the real, byte-exact files as fixtures.

Traps

  • Symmetric fixtures that hide encoding bugs
  • "The column is ours, so BinaryFormatter is safe", or reviving it with the compatibility package
  • Trusting culture data as a file format (fr-CA and fr-FR disagree)
  • Forgetting invariant globalization in containers
  • Missing culture="auto" in Web.config
  • Splitting on line feed in CRLF files
  • Failing a whole batch for one bad line
Interview drill

Four questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 4

What breaks silently when moving to modern .NET?

Answer out loud.

Model answer
  • Encoding.Default: ANSI code page → UTF-8, so Windows-1252 files garble
  • BinaryFormatter removed in .NET 9
  • Globalization: NLS → ICU, culture data changes
  • JSON defaults and casing; EF Core lazy loading and translation
  • System.Drawing Windows-only; distributed transactions need an opt-in
Question 2 of 4

Why is BinaryFormatter dangerous?

Answer out loud.

Model answer
  • The payload names the types to instantiate
  • Crafted payloads trigger gadget chains → code execution
  • No safe use on untrusted input; your own database isn't a trust boundary
  • Obsolete since .NET 5, removed in .NET 9
Question 3 of 4

How do you migrate data that was serialized with BinaryFormatter?

Answer out loud.

Model answer
  • Stop writing it: stage the raw input instead
  • Convert once: net472 tool with a restricted binder → JSON
  • Or System.Formats.Nrbf: read records without instantiating types
  • Format marker so both coexist; ban BinaryFormatter in CI
Question 4 of 4

How do you parse numbers from files safely?

Answer out loud.

Model answer
  • The file format defines the culture, not the server
  • Explicit encoding and NumberFormatInfo per source; TryParseExact for dates
  • Fixed-width field spec, not magic offsets
  • Quarantine bad lines with reason codes
  • Test under several cultures with byte-exact fixtures
