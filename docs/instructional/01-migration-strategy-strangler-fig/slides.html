Migration Strategy:
Strangler Fig vs Big Bang

.NET Framework 4.7.2 → .NET 10, one slice at a time

The questions this lesson answers

  • How would you approach modernizing a large .NET Framework application?
  • Big bang or incremental?
  • What would you migrate first, and why?
  • How do you know a migrated slice is finished?
  • You inherit a migration that stalled at 30%. What do you do in week one?
The thesis for the whole series

In fee billing, the migration is only done when you can prove the new system produces the same invoice, to the cent, for every account, and explain every place it intentionally doesn't.

Two strategies

Big-bang rewrite

Build a new system alongside the old one. Switch everyone over on one date.

Looks clean: no living with old code, no two stacks.

Strangler fig

Put a facade in front. Move one route or component at a time. Everything else falls through to legacy.

Each step deployed and rolled back on its own.

Big bang's three failure modes

  1. Value arrives late. Nothing ships until the end; priorities change first.
  2. Risk arrives all at once. Auth, data migration, the undocumented report: all in the final weeks.
  3. Rollback is all or nothing. The only way back is to abandon everything.

When big bang is reasonable

  • The application is small
  • It has good automated tests
  • It doesn't share state (like a database) with other systems

FeeBilling: none of the above.

The strangler fig pattern

The honest cost

  • Two stacks, two ORMs, one shared database, kept consistent for a long time
  • Transitional plumbing (like shared authentication) you'll throw away later

Worth it for a system that bills money: the alternative bets every invoice on one cutover weekend.

FeeBilling, as found

  • Advisory fees for ~40 wealth-management firms
  • ~350,000 accounts
  • Built 2011–2016 on .NET Framework 4.7.2
  • Maintained, not evolved

The brief

Enterprise clients now need Azure-hosted containers, SSO with their own identity provider, and SOC 2 evidence. A previous team got ~30% through a strangler-fig migration, then was reassigned.

A good ADR admits the costs

**Negative**

- Two stacks, two ORMs and a shared database have to be run and understood at once, for a long time.
- The transitional auth (remote authentication) couples new services to legacy uptime and adds a
  round trip per request.
- Each migrated route needs proof that it behaves like the legacy route, which is extra work per slice.

The strangler in miniature

Migrate = add a route and deploy. Roll back = remove it. Legacy doesn't change.

The rule

A migration change and a behaviour change must never ship together.

Reproduce legacy first. Prove it. Then fix separately, behind a flag, with sign-off.

A slice is done when…

  • Traffic is routed to the new service
  • Contract tests prove the same shapes; parity tests prove the same results
  • It's observable: logs, traces, metrics, and someone watching
  • Rollback has actually been exercised
  • The legacy code path is deleted, or frozen with a removal date

Reads roll back for free. Writes don't.

1 · Expand

Add the new shape alongside the old one. Both work.

2 · Migrate

Move data and code across. Legacy can still read everything.

3 · Contract

Remove the old shape once nothing uses it.

If the new service writes rows, legacy must still read them after a rollback.

Roll back one firm, not forty

Cut over firm by firm behind a feature flag.

A problem with one firm's invoices doesn't force a rollback for everyone.

Documents are a starting point, not the truth

Verify every ADR and handover note against the code and the calendar.

Your first week

  • Read the ADRs and handover, then verify them against the code
  • Build the risk register
  • Start the golden master for the fee engine
  • Handle the clock: .NET 8 support ends November 10, 2026

Traps

  • Answering with a technology list instead of a sequence
  • Starting with the fee engine because it's "the important part"
  • Refactoring legacy before capturing its output
  • Trusting the handover
  • Forgetting that writes break rollback
  • Never deleting the legacy path
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How would you approach modernizing a large .NET Framework application?

Answer out loud.

Model answer
  • Inventory → risk register
  • Shared libraries to netstandard2.0
  • YARP in front; migrate route by route, low-risk first
  • Characterization tests before the high-risk logic moves
  • Every step deployable and reversible; cut over tenant by tenant after shadow runs
Question 2 of 5

Big bang or incremental?

Answer out loud.

Model answer
  • Incremental, unless small, well-tested and no shared state
  • Big bang: late value, all the risk at once, all-or-nothing rollback
  • Honest cost: two stacks, shared database, transitional plumbing
Question 3 of 5

What would you migrate first, and why?

Answer out loud.

Model answer
  • Read-mostly, low-risk, on a real traffic path
  • Proves routing, auth, data access, CI and deploy end to end
  • FeeBilling: Accounts and Households
  • Not the fee engine: that waits for the golden master
Question 4 of 5

How do you know a migrated slice is finished?

Answer out loud.

Model answer
  • Routed · contract and parity tests pass · observable
  • Rollback exercised, not just described
  • Legacy path deleted or frozen with a date
  • Writes: legacy can still read them (expand and contract)
Question 5 of 5

You inherit a migration that stalled at 30%. What do you do in your first week?

Answer out loud.

Model answer
  • Read the ADRs and handover; verify against the code
  • Supersede ADR-0002: .NET 8 → .NET 10
  • Risk register from the code
  • Start the golden-master harness
  • Open questions (schema ownership) get owners and dates
