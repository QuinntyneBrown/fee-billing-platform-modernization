public static class PasswordHasher

            var bytes = Encoding.Unicode.GetBytes(salt + password);

    public static bool Verify(string salt, string password, string expectedHash)

The target

1 · An external identity provider

  • OpenID Connect with Microsoft Entra ID
  • Designed for per-client federation: employees sign in with their corporate accounts
  • FeeBilling never stores their passwords

2 · The gateway is a backend for frontend

  • Runs the OIDC authorization code flow
  • Holds the tokens: encrypted ticket or server-side session store
  • Gives the browser a cookie that's HttpOnly · Secure · SameSite
  • The access token never reaches JavaScript: less for an XSS bug to steal

3 · APIs validate bearer tokens

Sketch · target design
builder.Services.AddAuthentication()
    .AddJwtBearer(options =>
    {
        options.Authority = builder.Configuration["Auth:Authority"];
        options.Audience = builder.Configuration["Auth:Audience"];
    });

A YARP request transform attaches the access token when the gateway forwards.

Why not trust gateway headers?

Only safe if the APIs are unreachable except through the gateway.

Anyone who reaches an API directly can forge the header. Token validation is defence in depth.

Making the BFF work in production

Refresh tokens

Access tokens expire (typically ~1 hour). The BFF must refresh them, or sessions break silently.

Server-side ticket store

Saved tokens make cookies large. Keep only a session ID in the browser.

machineKey → Data Protection key ring

Sketch · target design
builder.Services.AddDataProtection()
    .SetApplicationName("FeeBilling")
    .PersistKeysToAzureBlobStorage(keyBlobUri, credential)
    .ProtectKeysWithAzureKeyVault(keyVaultKeyId, credential);

Without a persisted, shared key ring, every restart or scale-out invalidates every cookie.

If local passwords survive

  • Verify the old SHA-1 hash once, with a constant-time comparison: CryptographicOperations.FixedTimeEquals
  • On that successful login, rehash with ASP.NET Core Identity's PasswordHasher (PBKDF2)
  • Better: move those users to the identity provider too

Roles and policies

Role: a fact about a user

"This person is a billing admin."

Policy: a rule for an action

"May this caller start a billing run?"

Endpoints reference policies: change who may do something in one place.

FeeBilling's policies

PolicyReplacesRule
CanViewBillingGlobal authorize filterReviewer or admin + firm claim (or vendor staff)
CanStartBillingRunNothing: any signed-in userBillingAdmin + run's firm = caller's firm
CanApproveInvoicesRoles = "BillingAdmin"+ optional four-eyes rule
CanEditFeeSchedulesRoles = "ScheduleEditor"+ schedule's firm matches (templates have none)

Policies in ASP.NET Core

Sketch · target design
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanStartBillingRun", policy => policy.RequireRole("BillingAdmin"))
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());

app.MapPost("/api/billing/runs", StartRun)
    .RequireAuthorization("CanStartBillingRun");

"For this firm?" is a resource-based check: the role alone can't answer it.

The fix, in layers

  1. The tenant comes from a trusted firm_id claim, via a small ITenantContext
  2. Endpoints stop accepting a firm ID from callers who have one
  3. The data layer enforces it anyway: an EF Core global query filter
Sketch · target design
public class FeeBillingDbContext(DbContextOptions<FeeBillingDbContext> options, ITenantContext tenant)
    : DbContext(options)
{
    private readonly int? _firmId = tenant.FirmId;

    protected override void OnModelCreating(ModelBuilder modelBuilder) =>
        modelBuilder.Entity<Account>().HasQueryFilter(a => a.FirmId == _firmId);
}

EF Core 10: named query filters

Tenant and soft-delete filters can be ignored independently.

Before: one filter per entity, so ignoring filters removed both. Check the exact overloads for your version.

Vendor staff: an explicit mode

Model them as an explicit, logged mode, not as "no filter".

Otherwise a support engineer's query silently becomes cross-tenant, and nobody can tell afterwards.

Ways around a query filter

  • IgnoreQueryFilters
  • Raw SQL: FromSql, SqlQuery
  • Stored procedures: usp_GetBillableAum takes an account ID and trusts it
  • Dapper, which bypasses EF Core entirely
  • DbContext pooling, if the tenant is captured at construction

Each one a reviewed exception, backed by an architecture test or analyzer.

Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How do you migrate from Forms authentication to OIDC without logging everyone out?

Answer out loud.

Model answer
  • Map users to IdP identities, with reconciliation
  • Both sign-in paths for a window, switched per firm
  • Legacy trusts the new identity: SSO client or shared cookie
  • Old cookies expire (120 minutes); never a forced reset
Question 2 of 5

How do you enforce tenant isolation?

Answer out loud.

Model answer
  • Tenant from a trusted claim, never the query string or body
  • Data layer: EF Core global query filters
  • HTTP layer: a test that walks every endpoint
  • Bypasses are reviewed exceptions; vendor staff an audited mode
Question 3 of 5

Roles or policies?

Answer out loud.

Model answer
  • Role = fact about a user; policy = rule for an action
  • Endpoints reference policies: one change, one place
  • Policies combine roles, claims and resource checks
  • A fallback policy: nothing accidentally anonymous
Question 4 of 5

Where should tokens live in a browser application?

Answer out loud.

Model answer
  • Nowhere JavaScript can read them
  • BFF gateway runs OIDC, keeps tokens server-side
  • SPA gets an HttpOnly, Secure, SameSite cookie
  • Cookies bring back CSRF: antiforgery on state changes
Question 5 of 5

What would you fix first in this legacy authentication?

Answer out loud.

Model answer
  • The missing tenant check in the migrated Accounts API
  • The missing role check on starting a billing run
  • Rotate committed machine keys and passwords now
  • SHA-1 hashing matters less once passwords move to the IdP
