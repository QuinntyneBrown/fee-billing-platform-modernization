PeriodicTimer: ticks can't overlap

Sketch · target design
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30), timeProvider);
    do
    {
        await ProcessNextRunAsync(stoppingToken);
    }
    while (await timer.WaitForNextTickAsync(stoppingToken));
}

The next wait only starts after the work finishes. TimeProvider is injected so tests control time.

Graceful shutdown

Sketch · target design
builder.Services.Configure<HostOptions>(options => options.ShutdownTimeout = TimeSpan.FromMinutes(2));
  • Stop signals the token; running work gets ShutdownTimeout to finish
  • The default is short (30 seconds in recent versions): configure it
  • The orchestrator's grace period must be at least as long
  • An unhandled exception in a BackgroundService now stops the host

PeriodicTimer fixes

Overlap within one process.

It doesn't fix

Two instances picking the same run.

Only an atomic claim does.

Never select, then update

One atomic statement

Sketch · target design
WITH next AS (
    SELECT TOP (1) *
    FROM dbo.BillingRunQueue WITH (ROWLOCK, UPDLOCK, READPAST)
    WHERE Status = 'Pending'
    ORDER BY RequestedOn
)
UPDATE next
SET Status = 'Running', StartedOn = SYSUTCDATETIME()
OUTPUT inserted.Id, inserted.FirmId, inserted.PeriodEnd;

UPDLOCK locks the row it reads · READPAST makes other sessions skip locked rows. A second window gets the next run, not the same one.

Or: a conditional transition

Sketch · target design
var claimed = await db.BillingRuns
    .Where(r => r.Id == runId && r.Status == "Pending")
    .ExecuteUpdateAsync(s => s.SetProperty(r => r.Status, "Running"), ct);

if (claimed != 1) return;   // someone else got it

A row version column gives the same guarantee with optimistic concurrency.

Worse than it looks

Under read committed snapshot isolation, on by default in Azure SQL Database, readers don't block on writers.

Both instances read Pending. Both proceed.

Claims need an expiry

Without one

A worker that dies after claiming leaves its run Running forever.

A lease

A claimed-until time extended by a heartbeat, so another instance can reclaim abandoned work.

Or, once messaging arrives (lesson 16), let message redelivery drive the retry.

The core idea

Persist the plan before you process it.

A chunk table

Sketch · target design
CREATE TABLE dbo.BillingRunChunks
(
    RunId        int          NOT NULL,
    ChunkNo      int          NOT NULL,
    Status       varchar(20)  NOT NULL,   -- Pending | Complete
    CompletedOn  datetime2    NULL,
    CONSTRAINT PK_BillingRunChunks PRIMARY KEY (RunId, ChunkNo)
);

Chunks of ~500 billing units. Membership is decided once and stored: recompute it after a restart and accounts move between completed and pending chunks.

Chunk by billing unit, not by account

An account

With its own fee schedule.

A whole household

The household fee needs every member's AUM, then allocates back.

Chunk by account and household members land in different chunks.

Bounded parallelism

Sketch · target design
var options = new ParallelOptions { MaxDegreeOfParallelism = billing.MaxParallelChunks, CancellationToken = ct };

await Parallel.ForEachAsync(pendingChunks, options, async (chunk, token) =>
{
    await ProcessChunkAsync(run, chunk, token);
});

The limit comes from configuration and protects the database from being flooded.

Inside each chunk

  1. Load inputs set-based: a few queries per chunk, not per account
  2. Run the pure fee engine
  3. Add the invoices and save
  4. Mark the chunk Complete with ExecuteUpdateAsync
  5. Commit

Invoices and the "chunk done" marker commit together. That's the heart of resumability.

Retry-on-failure needs an execution strategy

Sketch · target design
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    db.ChangeTracker.Clear();                         // the lambda may run more than once
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    db.Invoices.AddRange(invoices);
    await db.SaveChangesAsync(ct);
    await db.Chunks.Where(c => c.RunId == run.Id && c.ChunkNo == chunk.No)
        .ExecuteUpdateAsync(s => s.SetProperty(c => c.Status, "Complete"), ct);
    await tx.CommitAsync(ct);
});

A safety net in the schema

Sketch · target design
CREATE UNIQUE INDEX UX_Invoices_Run_Account ON dbo.Invoices (RunId, AccountId);

When the commit's outcome is unknown

  • A connection drops during commit: did it succeed?
  • A retry inserts again
  • The unique index turns that into a clear error
  • Handler: if the chunk is already Complete, treat the violation as success

Traps

  • Porting the timer: PeriodicTimer fixes overlap in one process, not across instances
  • Select-then-update claiming: under read committed snapshot, both proceed
  • Claims with no expiry: a dead worker leaves its run Running forever
  • Chunking by account when billing is by household
  • Re-slicing on restart: persist chunk membership once
  • Beginning a transaction with retry-on-failure, outside an execution strategy
  • Shutdown timeouts that don't match between host and orchestrator
  • Blaming EF Core for the concurrency exception

Question 1 of 5

How would you replace a Windows Service in modern .NET?

Answer out loud.

Model answer
  • Host.CreateApplicationBuilder + a BackgroundService
  • DI, options, logging, graceful shutdown via the stopping token
  • AddWindowsService keeps the Windows option; same binary in a container
  • Fix the design: atomic claims, persisted chunks, idempotent writes
Question 2 of 5

Design a resumable batch job.

Answer out loud.

Model answer
  • Persist the plan: chunks stored with a status
  • Output + "done" marker in one local transaction
  • On restart, skip completed chunks
  • Unique constraints: a replayed chunk fails loudly
Question 3 of 5

How do you use a DbContext in parallel?

Answer out loud.

Model answer
  • You don't share one: it isn't thread-safe
  • IDbContextFactory: one short-lived context per unit of work
  • Parallel.ForEachAsync with a maximum degree of parallelism
  • EF Core's exception exposes the legacy bug
Question 4 of 5

How do you stop two instances processing the same work?

Answer out loud.

Model answer
  • One UPDATE with OUTPUT, using UPDLOCK and READPAST
  • Or a conditional update checked by row count or row version
  • Never select-then-update, especially under RCSI
  • A lease or heartbeat to reclaim a crashed instance's work
Question 5 of 5

What happens to in-flight work during a deploy?

Answer out loud.

Model answer
  • Stopping token + ShutdownTimeout; orchestrator grace period ≥ it
  • Uncommitted work rolls back and is retried after restart
  • Safe only because chunks commit atomically and writes are idempotent
