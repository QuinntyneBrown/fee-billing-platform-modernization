Modules and handlers become middleware

Classic ASP.NET on IIS

A fixed sequence of events per request. Modules subscribe to events. Handlers produce the response.

ASP.NET Core

A middleware pipeline, in exactly the order you write it. Modules → middleware. Handlers → endpoints.

The union type is the point

The mapping

HttpResponseMessageNo equivalent

HttpResponseMessage: no equivalent

  • Web API 2 let you build and return a raw response message
  • The ASP.NET Core 1 and 2 compatibility shim was removed in 3.0
  • A ported method still compiles, and ASP.NET Core serializes it as an object

The client gets JSON describing a message, not the response you meant.

Minimal APIs or controllers?

Minimal APIs

Less ceremony. TypedResults give accurate OpenAPI. Suit small vertical slices.

Controllers

Familiar to a Web API 2 team. Rich conventions and filters.

Pick one per service, write the decision down, be consistent. FeeBilling's first slice chose minimal APIs.

Traps

  • Porting HttpResponseMessage literally
  • Assuming error responses don't matter
  • Losing Web.config behaviour, like per-request culture
  • Middleware in the wrong order
  • A fallback policy that locks out health checks
  • Authentication that runs for every request, health checks included
  • IHttpContextAccessor to preserve old patterns · mixing both styles
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

What replaces Global.asax, HTTP modules and HTTP handlers?

Answer out loud.

Model answer
  • Program.cs: registration on the builder, then an explicitly ordered pipeline
  • Modules → middleware · handlers → endpoints
  • Application_Error → UseExceptionHandler with Problem Details
  • Application_EndRequest cleanup disappears: scoped services die with the scope
Question 2 of 5

Minimal APIs or controllers?

Answer out loud.

Model answer
  • Both fully supported
  • Minimal APIs: less ceremony, TypedResults + Results union → accurate OpenAPI
  • Controllers: familiar, rich conventions and filters
  • One per service, recorded and consistent; FeeBilling's reference is minimal APIs
Question 3 of 5

What happens to HttpResponseMessage and IHttpActionResult?

Answer out loud.

Model answer
  • No direct equivalent: the shim was removed in ASP.NET Core 3.0
  • Return TypedResults, or ActionResult of T in controllers
  • A ported HttpResponseMessage compiles and gets serialized as an object
  • FeeBilling: the invoice export becomes a file or stream result
Question 4 of 5

How does model binding differ?

Answer out loud.

Model answer
  • Web API 2: simple types from the URI, one complex type from the body
  • ASP.NET Core: inferred by convention, plus services, user, cancellation token
  • Bigger risk: automatic 400 validation problem details vs Message + ModelState
  • The AngularJS client reads Message, so contract-test errors
Question 5 of 5

How do you get the current user without HttpContext.Current?

Answer out loud.

Model answer
  • Pass it in: a ClaimsPrincipal parameter, or User in controllers
  • Pass the user or claim explicitly to services that need it
  • IHttpContextAccessor: rare, never in domain code
