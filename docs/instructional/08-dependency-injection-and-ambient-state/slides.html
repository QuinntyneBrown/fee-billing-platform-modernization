Two answers to question one

The cheat sheet

"Use IHttpContextAccessor."

The real answer starts with a question

What is the code actually using HttpContext for?

Ambient state

Data or a service that code reaches out and grabs from somewhere global, instead of receiving it as a parameter or through its constructor.

  • HttpContext.Current
  • HttpRuntime.Cache
  • A static logger
  • DateTime.Now, a dependency on the clock

A hidden parameter

public static decimal CalculateQuarterlyFee(int accountId, DateTime periodEnd)

What the signature says

An account ID and a period end

What it secretly needs

A live web request, a database connection hanging off it, a warm cache, the current time

Tied to a thread

IIS request thread

ASP.NET flows HttpContext.Current with the request

Timer thread

HttpContext.Current is null

Parallel.ForEach

Thread-pool threads: null

Code that "works" in IIS breaks the moment you call it from anywhere else.

Dependency injection is the fix

  • A class declares what it needs in its constructor
  • The composition root, at the edge, decides how to build things and how long they live
  • The dependency stops being hidden, and becomes replaceable
One context per request, stored on the request
legacy/FeeBilling.Data/DbContextFactory.cs
public static FeeBillingEntities Current
{
    get
    {
        var items = HttpContext.Current.Items;
        var db = items[ItemsKey] as FeeBillingEntities;
        if (db == null)
        {
            db = new FeeBillingEntities();
            items[ItemsKey] = db;
        }
        return db;
    }
}

Every Core class is static

What the built-in container doesn't do

  • Property injection
  • Interception or decorators
  • Child containers
  • Convention-based assembly scanning

But it covers

Constructor injection, three lifetimes, open generics, IEnumerable of a service, keyed services. Autofac only if you truly need more.

Three lifetimes

Singleton

Whole application. FeeEngine: pure and stateless.

Scoped

One per scope; in a web app, per request. FeeBillingDbContext.

Transient

New every resolve. A small validator.

Captive dependencies

Depend only on things that live as long as you do, or longer.

Sketch · the bug
// Registered as a singleton, so the first request's context lives forever.
public sealed class ScheduleCache(FeeBillingDbContext db)

Outlives its request · shared across threads · tracks stale entities

Let scope validation prove it

Development

ValidateScopes and ValidateOnBuild on by default: startup throws "cannot consume scoped service from singleton".

Production

Off by default: the app starts, and the bug ships.

Run integration tests in Development. Never disable validation to make the error go away.

A scope per unit of work

Sketch · target design
public sealed class BillingRunPoller(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // For each poll of the billing run queue:
        await using var scope = scopes.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<FeeBillingDbContext>();
        // … do the work; the scope disposes the context
    }
}

A hosted service is effectively a singleton: never inject the DbContext into its constructor.

Parallel work: a context per task

Sketch · target design (IDbContextFactory registered with AddDbContextFactory)

await Parallel.ForEachAsync(chunks, options, async (chunk, token) =>
{
    await using var db = await contexts.CreateDbContextAsync(token);

A bridge, not the destination

Microsoft.AspNetCore.SystemWebAdapters lets a netstandard2.0 library compile against System.Web.HttpContext, so shared code keeps working in both hosts.

  • Check which members it supports
  • Use it to buy time
  • It keeps the coupling; it just makes it portable
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How do you remove HttpContext.Current from a codebase?

Answer out loud.

Model answer
  • Find out what it's used for: DB context, user name, cache
  • Data (the user): read at the edge, pass as a parameter
  • Behaviour (context, clock, logger): constructor injection, right lifetime
  • IHttpContextAccessor only at the edge; SystemWebAdapters is a bridge
Question 2 of 5

What's a captive dependency?

Answer out loud.

Model answer
  • A longer-lived service holding a shorter-lived one
  • Singleton cache + scoped context: outlives the request, shared across threads
  • Scope validation catches it at startup (on by default in Development)
  • Never disable it to make the error go away
Question 3 of 5

How do you use a scoped DbContext from a background service?

Answer out loud.

Model answer
  • Inject IServiceScopeFactory; an async scope per unit of work
  • Resolve the context from the scope; dispose with it
  • Parallel work: IDbContextFactory, one context per task
  • Legacy shared one context in Parallel.ForEach; EF Core throws
Question 4 of 5

Would you keep Unity or Autofac, or use the built-in container?

Answer out loud.

Model answer
  • Built-in by default: constructor injection, lifetimes, open generics, IEnumerable, keyed
  • Autofac only for property injection, interception, child containers or scanning
  • Unity mapping: none → transient · hierarchical → scoped · container-controlled → singleton
Question 5 of 5

Why were the legacy fee calculators static, and why does that matter?

Answer out loud.

Model answer
  • Static classes can't take constructor dependencies, so they reached for ambient state
  • Untestable without a database and a web request
  • Forced the Windows Service to fake HttpContext on every thread
  • Unsafe in parallel; instance classes with explicit dependencies fix it
