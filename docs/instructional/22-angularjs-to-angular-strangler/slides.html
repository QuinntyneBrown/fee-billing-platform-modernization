ngUpgrade: one page, two frameworks

What you get

  • AngularJS services upgraded for Angular
  • Angular components downgraded into AngularJS templates
  • Shared in-memory state, in-app navigation

What it costs

  • Both frameworks in the bundle
  • Digest cycle and change detection interact
  • Old and new deploy together
  • Legacy scripts aren't bundled at all

Route-level: the same strangler as the APIs

Nothing shared in memory: only APIs and the auth cookie. Crossing over is a full page load. Deploys are independent.

Which one fits?

ngUpgrade

Screens tightly interwoven, sharing in-memory state.

Route-level

Screens are separate routes: billing review, run invoices, schedules, accounts.

FeeBilling: route-level. Separate screens, independent deploys, no hybrid bootstrap. Record it in an ADR.

The detail that shows you've done it

Browsers never send the fragment to the server.

Real paths hand the route to the server

Hash routing

Server sees /. The route hides in the fragment.

Real paths

Server sees /billing-review/runs/42 on a bookmark or refresh.

The Angular host must answer any path under its prefix with the app's index page. Without that fallback: 404.

Generate the client from OpenAPI

API changes shape → client regenerates → the build fails, not the page.

The client trusts the schema, not the wire

OpenAPI document says

runId, accountNumber

The API actually sends

RunId, AccountNumber

Compiles cleanly, renders blanks. Make the document and the serializer agree, and prove it with a test.

Polling that stops by itself (FB-262)

Sketch · target design · billing-run-review.ts
timer(0, 5000).pipe(
  switchMap(() => this.api.getRun(this.runId)),
  takeWhile(run => run.status === 'Pending' || run.status === 'Running', true),
  takeUntilDestroyed(this.destroyRef),
).subscribe(run => this.run.set(run));

Ends when the run finishes, or when the component is destroyed via its DestroyRef.

Two more legacy shortcuts go away

Hard-coded firms (FB-204)

An API call, scoped by the caller's firm claim (lesson 20). Vendor staff see all firms.

Total ignores the filter

A server-side total for the applied filter, returned with the page of rows.

Dates

  • Timestamps in UTC with an explicit offset
  • Date-only values, like the period end, as plain dates
  • Formatted for display in one place

Lesson 11: a date without a time-zone marker is read as local time in the browser.

The double-click (FB-247): do both

UX

Disable the start button while a request is pending.

The fix

One Idempotency-Key per user action. A repeated key returns the original run (lesson 12).

Same origin, same cookie

The cookie flows with every request, with no code at all. No token for a cross-site scripting bug to read.

Cookies bring back CSRF (FB-279 is still open)

  1. Server issues a readable cookie: XSRF-TOKEN
  2. Angular's HttpClient echoes it in an X-XSRF-TOKEN header
  3. ASP.NET Core antiforgery validates it

Two gotchas

Relative URLs only

Angular attaches the header to mutating requests with relative URLs. An absolute URL silently skips it.

JSON endpoints

Built-in middleware validates only some endpoint types. You may need an endpoint filter calling ValidateRequestAsync. Verify for your version.

401 → full-page sign-in

Navigate the whole page to sign in, rather than showing an in-app error.

The gateway owns the sign-in flow.

One site, two apps

If the navbar, colours and typography change on one click, users experience the boundary as "the site broke".

  • Shared design tokens: CSS variables for colours and spacing
  • An identical navbar in both apps

Playwright, end to end

1Start a run
2Watch its progress
3Review the invoices
4Approve

Crosses AngularJS → Angular → back. Write it against legacy first, get it green, keep it green as the screen moves.

Traps

  • Routing hash URLs at the proxy: fragments never leave the browser
  • Relative API URLs under a sub-path
  • Porting FB-247 as "disable the button": the fix is server idempotency
  • @for over fifty thousand rows: virtual scroll plus server paging
  • Tokens in localStorage; and with cookies, XSRF protection is mandatory
  • Casing drift between the OpenAPI document and the real JSON
  • Copying the IE cache-busting hack: use proper Cache-Control on the server
  • Two different-looking apps
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

How do you migrate an AngularJS app incrementally?

Answer out loud.

Model answer
  • Route-level strangler behind the same gateway as the APIs
  • New app owns whole screens on real paths; AngularJS keeps the rest
  • Full-page links across the boundary; client-side redirect for old hash bookmarks
  • One screen fully done, tests included; Playwright across the boundary
Question 2 of 5

ngUpgrade or route-level?

Answer out loud.

Model answer
  • ngUpgrade: tightly interwoven screens sharing in-memory state
  • Route-level: separate routes
  • Independent deploys; no two frameworks' change detection in one page
  • FeeBilling: separate screens, unbundled scripts → route-level, in an ADR
Question 3 of 5

How does the single-page app authenticate without storing tokens?

Answer out loud.

Model answer
  • Gateway as backend for frontend: runs OIDC, holds the tokens
  • Same origin: the HttpOnly session cookie is sent automatically
  • XSRF token cookie, echoed in a header on mutating requests, validated by the server
  • Plus SameSite cookies
Question 4 of 5

How do you keep the front end and API contracts in sync?

Answer out loud.

Model answer
  • Generate the TypeScript client from OpenAPI in CI
  • Contract drift fails the build, not the page at runtime
  • Test that the document matches what the serializer emits
  • Classic mismatch: PascalCase vs camelCase
Question 5 of 5

How do you show fifty thousand rows?

Answer out loud.

Model answer
  • Cursor paging on the server
  • CDK virtual scroll viewport in the browser: only visible rows in the DOM
  • Never load everything and filter client-side (legacy: 40,000 invoices)
