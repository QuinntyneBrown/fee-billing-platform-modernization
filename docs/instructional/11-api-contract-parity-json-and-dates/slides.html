JSON and Dates

FeeBilling already has one of these regressions in the code.

The idea underneath

The contract is what the legacy endpoint actually emitted on the wire, not what the C# class looks like.

Reference loops

Newtonsoft · Ignore

Silently omits the property that would create the cycle.

STJ · IgnoreCycles

Writes null for the cycle instead. Different output.

Better: stop serializing entities. Project to DTOs, and cycles can't happen.

"TIERED"

String enum converter emits

"Tiered": breaks JavaScript comparisons and the RegularExpression("TIERED|BLENDED|FLAT") attribute

Input is more forgiving than output

  • Web defaults read property names case-insensitively
  • Numbers written as strings are accepted
  • So old front-end requests usually still bind
  • It's the responses that break

Decimals keep their scale

{ "Amount": 5312.50 }

The trailing zero goes out on the wire. Money formatting is part of what the client sees, so snapshots include it.

Handover issue #3, in one line.

DateTime.Kind decides the suffix

KindWritten asBrowser reads it as
Utc…T00:30:00ZUTC, converted to local
Local…T00:30:00 with an offsetThat offset
Unspecified…T00:30:00 (no suffix)Local time

Values read from SQL Server come back Unspecified, in EF6 and EF Core: datetime2 has no time zone.

One missing line, one day wrong

database/seed/010-seed-q3-2026.sql
-- LastValuedAt is UTC: the valuation job for Sep 30 finished at 8:30 p.m. Eastern.
DECLARE @valued datetime2(0) = '2026-10-01T00:30:00';

With the Z

Eastern browser shows September 30, 8:30 p.m.

Without the Z

Shows October 1. Every user west of UTC, after 8 p.m.

Instants and calendar dates are different things

OpenedOn: a SQL date

Arrives as midnight, Unspecified, and goes out with no suffix. The date filter shows it correctly.

"Mark every date as UTC"

Open dates start shifting back a day for users west of Greenwich.

DateTimeOffset for instants. DateOnly for dates.

Capture before you migrate

1Record the real legacy response for every function in api.service.js
2Success and error cases; commit them
3Snapshot-test the new endpoint (e.g. Verify), volatile fields scrubbed
4Assert names, types and date suffixes, not just status codes

Interview drill

Four questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 4

What breaks silently when you move an endpoint from Web API 2 to ASP.NET Core?

Answer out loud.

Model answer
  • Property casing: Newtonsoft keeps C# names; ASP.NET Core camel-cases
  • DataSet serialization: the Table wrapper disappears
  • Error bodies: Message and ModelState vs problem details
  • Enums, reference loops, and DateTime Kind (the trailing Z)
  • FeeBilling: the migrated DTO already lost its UTC marker
Question 2 of 4

How do you prove an API contract didn't change?

Answer out loud.

Model answer
  • Capture real legacy responses, including errors, and commit them
  • Snapshot-test the new endpoint's raw JSON, volatile fields scrubbed
  • Assert names, types and date formats, not just status codes
  • Write them before moving the endpoint; consumer-driven contracts for many consumers
Question 3 of 4

DateTime or DateTimeOffset?

Answer out loud.

Model answer
  • DateTime carries a Kind; values from SQL come back Unspecified
  • DateTimeOffset: explicit offset, the safer default for instants
  • DateOnly for dates with no time: open date, period end
  • The type changes the JSON: new version; legacy route gets an explicit UTC Kind
Question 4 of 4

Why did the dates shift by a day?

Answer out loud.

Model answer
  • Stored in UTC, serialized without a Z (Kind Unspecified)
  • The browser parsed it as local time
  • 8:30 p.m. Eastern Sep 30 = 00:30 Oct 1 UTC → shows October 1
  • Fix: restore the UTC Kind (value converter) + a contract test asserting the Z
