Shared Database and
Schema Ownership

An old app and a new app share one database. Who changes the schema, and how?

The questions this lesson answers

  • Two ORMs share one schema: who owns changes?
  • How do you change a schema that an old app and a new app both use?
  • Should the application run its migrations on startup?
  • How do you know whether a stored procedure is still used?
  • When do you finally split the shared database?
Why it matters

The schema is the contract between the old system and the new one.

Every schema change during a migration is a contract change. Treat it like a public API change.

## Consequences

- Two models (the EDMX and EF Core) describe the same tables and can drift.
- Any schema change can break the legacy app, the new services, or both.
- Database-per-service is deferred, not abandoned.

The rule while legacy runs

EF Core owns the schema, but legacy still has a veto.

Every change stays backward compatible with the legacy application until legacy is retired.

A drift test catches what migrations can't

Sketch · target design
// For every mapped property, compare EF Core's metadata with the real column.
var columns = await LoadColumnsAsync(connection);   // INFORMATION_SCHEMA.COLUMNS
foreach (var entity in db.Model.GetEntityTypes())
foreach (var property in entity.GetProperties())
{
    var column = columns[(entity.GetTableName(), property.GetColumnName())];
    Assert.Equal(column.Precision, property.GetPrecision());
    Assert.Equal(column.Scale, property.GetScale());
}
// FeeTiers.AnnualRate: database 9,6 · mapped 18,2 · fails until the mapping is fixed

On this repository it fails on the annual rate. That's exactly what you want.

Parallel change

Never change a shape in place. Add the new shape next to the old one, move everyone across, then remove the old shape.

Expand and contract: five steps

  1. Expand · add the new column or table, nullable; nothing notices
  2. Backfill · copy existing data into the new shape, in batches
  3. Dual write · keep both shapes current, from the app or a trigger
  4. Switch reads · point the new code at the new shape
  5. Contract · remove the old shape once no consumer needs it

During a strangler fig, "contract" usually means after legacy is retired.

Example 1: additive and safe

Sketch · target design
ALTER TABLE dbo.BillingRunQueue ADD IdempotencyKey varchar(64) NULL;

CREATE UNIQUE INDEX UX_BillingRunQueue_IdempotencyKey
    ON dbo.BillingRunQueue (IdempotencyKey) WHERE IdempotencyKey IS NOT NULL;
  • EF6 Database-First selects only the columns in its storage model: invisible to legacy
  • usp_EnqueueBillingRun keeps inserting rows without a key; the filtered index ignores them
  • No contract step: the column stays

Check before shipping

Writing to a table with a filtered index requires the quoted identifier setting to be on.

A stored procedure keeps the setting it was created with, so check usp_EnqueueBillingRun first.

Example 2: needs all five steps

database/billing/001-schema.sql · dbo.Accounts
LastValuedAt    datetime2(0)    NULL,           -- written by the nightly valuation job, in UTC

The type doesn't say UTC. That's the root of handover issue #3: dates come back with an unspecified kind, and the browser treats them as local time.

Changing the type in place would break the EDMX, which expects a plain DateTime.

LastValuedAt → a datetimeoffset column

  1. Expand · new nullable datetimeoffset column, UTC in its name
  2. Backfill · from the old column, in batches
  3. Dual write · the valuation job writes both columns
  4. Switch reads · EF Core maps the new column; new APIs read it
  5. Contract · drop the old column after legacy and the EDMX are gone

Legacy notices none of this. The drop goes on the decommissioning checklist.

Two rules

Never rename or drop in one step

EF Core happily generates a valid rename-column migration. Legacy breaks on its next query.

Never add NOT NULL without a default

Legacy inserts don't know the column exists, and they fail.

A schema change that's really a behaviour change

Sketch · a unique index across firm and period end
CREATE UNIQUE INDEX UX_BillingRunQueue_Firm_Period ON dbo.BillingRunQueue (FirmId, PeriodEnd);
  • Legacy's double-click now throws an error instead of creating a second run
  • Legacy behaviour changed through the database: it needs the same sign-off as a code change
  • If duplicate rows already exist, the index won't even create

Migrations at startup?

db.Database.Migrate();   // on application start

In a multi-instance or regulated deployment: don't.

Why not at startup

  • The app's SQL login needs DDL rights: breaks least privilege
  • Instances starting at once race each other (newer EF Core takes a lock; check your version)
  • A failed migration takes the app down mid-rollout
  • Nobody reviewed the SQL that ran against production

Generate, review, run in the pipeline

dotnet ef migrations script --idempotent --output migrate.sql
dotnet ef migrations bundle --output efbundle

1 · Pull request

The SQL is reviewed with the code.

2 · Pipeline step

Script or bundle runs with an elevated login.

3 · Deploy the app

Its login reads and writes data, but can't change the schema.

Traps

  • Assuming the ORM will figure it out: migrations compare model and snapshot, never the live database
  • Mapping an existing table after the baseline: the next migration tries to create it
  • Renaming or dropping in one step
  • Adding NOT NULL without a default: legacy inserts fail
  • Treating a schema change as purely technical when it changes legacy behaviour
  • Running migrations at startup
  • Deleting procedures based on a repository search: observe a full quarter
  • Forgetting the reporting database: a third model with its own owner question
Interview drill

Five questions

After each question, pause and answer out loud. Then compare with the model answer.

Question 1 of 5

Two ORMs share one schema. Who owns changes?

Answer out loud.

Model answer
  • Exactly one owner, written down in an ADR
  • EF Core migrations: same PR as the code, reviewed, versioned
  • The EDMX goes read-only, regenerated from the database
  • Backward compatible with legacy until it's retired
  • A drift test against the real column types
Question 2 of 5

How do you change a schema that an old app and a new app both use?

Answer out loud.

Model answer
  • Expand, backfill, dual write, switch reads, contract
  • Drop the old shape only after legacy is gone
  • Never rename or drop in one step; never NOT NULL without a default
  • Additive, nullable changes are invisible to EF6 Database-First
Question 3 of 5

Should the application run migrations on startup?

Answer out loud.

Model answer
  • Not in a multi-instance or regulated deployment
  • DDL rights for the app, races, failed rollouts, unreviewed SQL
  • Idempotent script or migration bundle, reviewed in the PR
  • A pipeline step with an elevated login; the app runs least-privilege
Question 4 of 5

How do you know whether a stored procedure is still used?

Answer out loud.

Model answer
  • The repository only shows what the repository calls: 6 of 14
  • Reports, agent jobs and scheduled tasks live elsewhere
  • Procedure stats view, Query Store or Extended Events
  • Observe a full billing cycle
Question 5 of 5

When do you split the shared database?

Answer out loud.

Model answer
  • When ownership is clear and no cross-service joins remain
  • Ownership map → schema and login per service → views as contracts → CDC or events
  • Sharing was right for the first slices: no synchronization
  • Deferred, not abandoned
